# 統合要件と実装の境界

このファイルの後続フェーズは設計方針であり、実装済みの機能を意味しません。今回の完成単位はPhase 1とPhase 2の主要機能です。

## Phase 1 — 実装・自動検証済み

- 256×256都市、APIキー不要の生成、OSM失敗時の明示付きサンプル。
- 接続需要・河川・鉄道・合成丘陵を考慮する階層道路、接道に沿う回転建物。
- 窓・入口・屋根・ベランダ・店舗庇などの雛形、PNG、Sponge v2 `.schem`。
- 複数シード、重複・切断・接道・NBT形式、旧MVPの互換性テスト。

ゲーム内の貼り付け・歩行検証は未完了です。自動検証と実機検証を区別します。

## Phase 2 — 主要機能を実装済み、一部継続

道路曲率・方位・交差点・幅・階層・間隔・区画分布、河川・鉄道・標高タグを分析し、複数地域の統計を混合。駅前・旧市街・郊外・新興住宅地・工業地・河川沿いの構造差と建物のバリエーションを生成します。v0.2.1で名前付き都市・区・地区と占有敷地の管理を追加しました。

残る項目は実DEM、立体交差を完全に分離した分析、庭・通路を含む宅地分割、非矩形建物、多様な都市規模の校正です。現在の6需要拠点は配置テンプレートを使用し、Minecraft都市の密度も実都市と同一ではありません。

## Phase 3 — 対話型編集（未実装）

日本語の「駅」「梅田のような駅前」「道路沿いのコンビニ」「住宅街」「新しい区」「再開発」「公園と小学校」「外観の改善」「路地」「河川と橋」は、以下の共通編集フローで扱う予定です。

1. 入力は `project.json`、日本語、対象の区/地区/建物IDまたは範囲。曖昧な「ここ」は明示的な選択範囲またはプレイヤー位置を必要とする。
2. 構造化計画へ変換。元スナップショットのダイジェスト、座標系、対象範囲、作成/更新/削除の一覧、seed、建築仕様、理由を含める。
3. 範囲外への変更、衝突、接道、地形・河川・鉄道の横断を検証。差分JSONと変更前後のプレビューを保存する。
4. 建築物の削除や再開発など重要な変更は承認を待つ。承認は計画内容と元スナップショットに結び付け、承認後に内容を変えない。未承認の案をワールドに適用しない。
5. 適用前に元データが変わっていれば拒否して再計画する。適用履歴と逆差分を記録し、取り消し・復元にも同じ競合検査を使う。

APIキーなしの場合は対応範囲を明示した日本語ルールパーサを用意し、解釈できない指示を黙って別の操作へ置換しません。AIは建築仕様のJSONを作り、Pythonの建築器が許可されたブロックを配置します。

Web地図はiPhone向けのタップ・ドラッグ選択、チャット、差分確認と承認を提供する予定です。ゲーム内2点選択と同じローカルX/Z範囲へ変換します。現段階ではWebサーバー・地図UI・自然言語編集のコマンドはありません。

## Phase 4 — Minecraftと大規模拡張（未実装）

- PaperプラグインがプレイヤーUUID、ディメンション、現在位置、2点選択、権限を扱う。ワールド座標と都市座標の変換は明示的な原点・回転を保存する。
- 認証された編集ジョブを受け、サーバーのメインスレッドでブロック配置数を制限し、進捗・中断・逆差分を管理する。無承認の広範囲置換や任意サーバーコマンド実行を避ける。
- 都市外への拡張は区/チャンクごとに計画し、境界上の道路・鉄道接続を共有する。既存区画を保持し、変更されたチャンクだけ構築する。
- Windows・8GB RAM・HDDの1人用サーバーを想定し、都市生成をPaperのtick処理から分離する。まず256×256でメモリ・ディスク待ち・貼り付け時間を実測し、生成と貼り付けの同時実行を評価してから拡張する。現行の全都市配列方式は最大512×512で、大都市用の分割エンジンではない。
- 内装・部屋割り・家具・階段・屋上設備を用途別に追加し、歩行ルートを検証する。
- Bedrockは後続作業。`.mcworld`の生成・Javaブロック変換・統合版実機確認を別途実装する。GeyserMC/Floodgate経由の接続と`.mcworld`出力は別機能として検証する。
